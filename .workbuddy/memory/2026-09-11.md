# 2026-09-11

## 修复：连续交接后「实际处理人」被覆盖（皇上报的 bug）

**皇上反馈**：钱七 → 孙八 → 周九 两段交接后，流程链显示成「孙八处理的」，但实际是钱七处理的（钱七 9/8 提交，9/10 才交接）。

**定位过程**：
- 查 `flow_task_handover`：9/10 16:05 钱七→孙八（已通过）、9/10 17:48 孙八→周九（已通过）。
- 查 `flow_task_node`（该配置下）：两条节点 `问题整改` / `行领导审核` 的 `handler_user_id = emp0007 周九`，但 `transfer_from_user_id = emp0006 孙八` ❌ —— 而 `handle_time` 是 **2026-09-08 17:03 / 17:07**（早于两次交接），说明真正提交的人是**钱七**。
- **根因**：`FlowTaskHandoverService.transferNode()` 每次交接都无条件 `n.setTransferFromUserId(from)`，第二次交接把第一次的留痕（钱七）**覆盖**成了当时的 handler（孙八）。

**修复（后端 2 个文件）**：
1. `FlowTaskHandoverService.transferNode()`：`transferFrom` 为空时才写，**已提交节点的留痕不能被后来的接手人覆盖**（`if (n.getTransferFromUserId() == null || isEmpty)`）。
2. `FlowTaskService.transfer()`（转办）：同样的"只记最早那一位"判断。
3. `FlowTaskService` 新增 `clearTransferFrom(taskNodeId)`：节点被**本人提交**后，实际经办人就是本人 → 清掉此前的交接/转办留痕（否则「先被交接、再由接手人提交」的节点会一直显示成原处理人做的）。在 `submit()` 的**退回分支**与**通过分支**两处 `updateById` 之后各调一次。
   - ⚠️ 坑：MyBatis-Plus 的 `updateById` **忽略 null 字段**，置空必须走 `LambdaUpdateWrapper.set(..., null)`（已按此实现，并 import `update.LambdaUpdateWrapper`）。

**留痕语义（现在自洽）**：`transfer_from` = 已提交节点的**实际经办人**；未提交节点则表示「席位原本归属人」。前端 `formatHandlerWithTransfer` 保持不变 —— 已提交节点输出「钱七 emp0005（现 周九 emp0007）」。

**数据修复**：`flow_task_node` 两条被覆盖的记录 `transfer_from` 由 `emp0006 孙八` 改回 `emp0005 钱七`（WHERE 精确限定 id + 当前值，`ROW_COUNT()=2`）。

**验证**：`mvn -q -o compile` 0 error；重启后端（PID 31871）后调 `GET /flow-task/detail/FLOWTASK202609081630581515793230` → 两条节点均为「当前归属 周九 / 实际留痕 钱七」✅。前端未改，dev server 隔夜被回收，已重启（9528）。
