## 修复 back 仍返回任务处理页（hash 模式坑）

- 现象：上一版改完，从关联页进详情点返回，仍回任务处理页。
- 根因：路由是 **hash 模式**（`router/index.js:198` 的 `mode:'history'` 被注释）。`$router.resolve(...).href` 在 hash 模式下返回带 `#` 的 `#/flow-dispatch/task-link?...`；ProcessDetail `$router.push(back)` 推 `#` 开头的字符串会被 vue-router 当成「仅 hash 变化」，path 不变 → 落回默认任务处理页。
- 修复：TaskLink `openProcess` 改用 `$router.resolve(...).route.fullPath`（不含 `#`）；ProcessDetail `goBack()` 加防御，`back` 若以 `#` 开头则先 `slice(1)`。eslint 0 error。
- 结论（重要约定）：hash 模式下要拿可 push 的完整路径，用 `route.fullPath`，**不要用 `.href`**。

### 交接范围语义澄清（皇上指出歧义，先不动代码）
- 皇上原话要点：钱七只是**中间节点处理人**，但**同样有交接需要**——调走了，他**处理过的节点所在的那条任务**要给别人看，就把这条任务给别人。
- 臣原实现的偏差：把「已提交的历史节点」排除在可交接范围外（理由是审计），只覆盖 ①owner=我的期次整期 ②我在**进行中**任务下**未提交**的节点（`nodesOf(otherTaskIds, from, 0)`，otherTaskIds 来自 `runningTaskIdsOf`）。钱七的节点全在**已结束**任务里且已提交 → 两个范围都进不去 → 弹窗落空态。
- **正确锚点（理解）**：交接的判定不应是「我手上还有没有活」，而应是「**这条任务是不是因为我的节点席位而出现在我的列表里**」。可见性 SQL（FlowTaskNodeMapper.xml `selectMyTaskGroups` / `selectMyTodo`）= `t.owner_id = 我 OR tn.handler_user_id = 我`，且任务状态含 `已结束`。所以「已提交/已结束」的节点同样制造可见性，必须可交。
- 修正方向：范围②去掉 `submitStatus=0` 与「进行中」双重限制 → 该配置下**我名下全部节点（不论提交状态、不论任务状态）**处理人 A→B；`transferNode` 已写 `transfer_from_user_id/name` 留痕。
- 已确认无副作用：未提交节点的提交校验 `FlowTaskService:1350` 只针对待办节点；`current_handler_id` 由 `submit_status=0` 的节点重算（`FlowTaskService:1083`），换历史节点不影响流转；`FlowFormRecordMapper.xml:81` 按 `handler_user_id` 查「我经手的表单记录」，换人后接手人即可看到这些记录——正是皇上要的「给别人看」。
- 待皇上拍板 3 点：①范围是否含已提交/已结束节点 ②历史节点换人后界面是否标注原处理人（留痕展示） ③交接后钱七是否彻底不可见（转移）还是双方可见。

## 修复「同一个提示弹两次」（前端全局）

皇上反馈：前端每次请求，后端返回的信息会提示两次。查出**两处根因**：

1. **错误提示双弹**：`BaseAxios` 响应拦截器 `code !== 200` 时已 `Message(...)` 弹一次，业务侧 `catch` 里又写 `this.$message.error((e && e.message) || 'xxx')` 弹第二次（文案一模一样，因为拿的就是 `e.message`）。全项目 39 处 `$message.error`，其中 37 处属这种重复。
2. **成功提示双弹**：`HandoverModal.vue` 提交成功后自己 `$message.success('交接申请已提交，等待审批')` + `$emit('success')`，而 `taskprocess/index.vue` 的 `onHandoverSuccess()` 又 `$message.success('交接申请已提交，等待部门管理员审批')` → 两条。其余两对（`AddTaskLinkModal`→`onLinkAdded`、`GeneratePeriodModal`→`onGenSuccess`）父组件回调里**没有**提示，未受影响。

**改法**：
- 新增 `src/utils/notify.js`：`notifyError(message, duration)` 是错误提示的底层唯一出口，**相同文案 800ms 内只弹一次**（页面并发拉多个接口一起失败时不刷屏）。

## 答疑：utils 各文件用途与「搬内网要带什么」

皇上追问「utils 下那些 js 都是干嘛的，能不能删，搬到内网是不是要额外移东西」。对比 gzfb 后结论：

- **gzfb 的 `gzfb-front/src/utils/` 只有 1 个文件**：`request.js`（内网框架兜底）。它没有 auth/validate/get-page-title，是因为 gzfb 把登录态放在 Vuex（`permission.js` 用 `store.getters.userInfo`），走的是另一套脚手架写法 —— **不是内网框架的要求**。
- flow 的 6 个文件都是「脚手架自带 + flow 自研」，全部被业务/布局代码直接引用，**删任何一个都要改调用方**：`auth.js`（permission、store·user、HandoverModal）、`get-page-title.js`（permission）、`validate.js`（Sidebar Link/SidebarItem、SvgIcon）、`index.js`（FlowChain、ProcessDetail、HandlerFlowDetail、formdesigner）、`notify.js`（main.js 的 `$notifyError`，业务 catch 37 处）、`request.js`（BaseAxios）。
- **搬内网时的结论**：`service/` 与 `utils/` **照常整体复制、无需挑拣**。唯一「内网专属」的是 `utils/request.js` —— 内网框架已挂全局 `get/post`，该文件里的 `if (typeof window.get !== 'function')` 保护会让它自动不生效，**带着零影响**；反过来它也不能删，本地开发要靠它兜底。后端同理：`GlobalExceptionHandler`（flow 原本就有，已对齐 gzfb 写法）与新增的 `ParamUtil` 都是 `base/` 下的通用件，gzfb 也有同款。
