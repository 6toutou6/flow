# 线性顺序流转工作流系统｜完整方案

## 一、系统概述

### 业务场景
管理员先**设计流程模板**：把一个业务（如"分散采购"）拆解为一条**有序的流程节点链**——下发 → 需求设计 → 执行设计 → 合同设计 → 签订合同 → 结束。每个节点配置自己要填写的表单字段。基于模板下发一个任务后，任务按节点顺序逐个流转：当前节点处理人填完表单、提交时**指定下一个节点的处理人**，依此推进，直到"结束"节点任务完成。

> 本系统是**顺序流转工作流**，区别于并行表单收集：不是所有人同时填一张表，而是一步一步往前走，每步处理人不同、每步填的字段不同。

### 举个例子（分散采购）
1. 流程管理员新建模板"分散采购流程"，设计 6 个节点：下发 / 需求设计 / 执行设计 / 合同设计 / 签订合同 / 结束
2. 在"需求设计"节点配置字段：需求编号（文本，必填）、需求日期（日期）
3. 在"合同设计"节点配置字段：合同金额（数字）、合同附件（文件）
4. 下发任务"2026年8月分散采购"，指定**第一个节点（下发）的处理人** = 张三
5. 张三登录 → 任务处理页 → 待办显示该任务 → 处理：填写下发信息 → 指定下一节点（需求设计）处理人 = 李四 → 提交
6. 李四登录 → 待办 → 处理需求设计节点的表单 → 指定下一节点处理人 → 提交
7. ……依此流转，直到"结束"节点处理人提交，任务状态变为"已完成"

### 角色定义
1. **超级管理员**：用户管理、角色权限、基础配置
2. **流程管理员**：创建流程模板、设计节点链与节点表单、下发任务、查看流转数据
3. **处理人**：在任务处理页接收当前节点的待办，填写本节点表单、指定下一节点处理人后提交

### 核心能力清单
1. 流程模板管理（启用/停用、版本管理、复制）
2. **流程节点链设计**：可视化添加/排序节点，区分开始节点 / 中间节点 / 结束节点
3. **节点级表单设计**：每个节点单独配置要填写的字段
   - 字段类型：单行文本、多行文本、数字、日期、单选枚举、多选枚举、文件、图片
   - 字段属性：标签、占位文字、是否必填、排序、提示文案、最大长度、文件大小限制、允许后缀
4. 任务下发：基于模板创建任务，指定**首个节点处理人**、填报起止时间、任务说明
5. 任务处理：处理人在待办里填写当前节点表单，提交时指定下一节点处理人
6. 流转进度可视化：el-steps 展示任务走到哪一步、谁处理过、当前谁处理
7. 数据后台：任务维度统计与列表，查看每个任务的流转记录与各节点表单数据

## 二、总体架构分层
1. **前端（Vue.js + Element UI）**
   - 流程设计器：节点链 + 节点字段画布 + 属性面板
   - 任务下发：选模板 → 填任务信息 → 指定首节点处理人
   - 任务处理：我的待办 + 处理弹窗（动态表单 + 指定下一处理人 + 流转进度）
   - 数据后台：任务列表 + 流转详情
2. **后端（Spring Boot + MyBatis-Plus）**：模板/任务/数据的 CRUD 与流转核心事务
3. **存储**：MySQL（业务结构化数据），附件第一版存文件名文本（后续接对象存储）

## 三、核心功能详细设计

### 3.1 流程模板模块
1. 新增/编辑/复制/删除模板（基础信息：模板名称、分类、全局提示）
2. **设计流程**（核心）：三栏布局
   - 左栏「节点链」：垂直节点列表，每项 = 节点名 + 类型徽章 + 字段数 + 上下移/删除；首节点强制为"开始"、末节点强制为"结束"
   - 中栏「字段画布」：当前选中节点的字段列表，可增删/排序
   - 右栏「属性面板」：上半 = 节点属性（名称/标识/类型/提示/是否需要指定下一处理人），下半 = 选中字段属性
3. 保存流程：保存节点链 + 每个节点的字段，模板版本号 +1
4. 模板启用/停用、版本记录（已下发任务锁定当时版本）

### 3.2 任务下发模块
模板 ≠ 任务（模板是图纸，任务是一次实际工作）
1. 选择流程模板（仅启用的）
2. 设置任务名称、任务说明、起止时间
3. **指定首个节点（开始节点）的处理人**（单选）
4. 下发任务，系统自动把首个节点的待办推给该处理人

### 3.3 任务处理模块（流转核心）
1. **我的待办**：查询当前登录用户作为处理人、且未处理的任务节点
2. **处理弹窗**：
   - 任务信息 + 流转进度（el-steps：已处理 success / 当前 process / 未处理 wait）
   - 动态表单：根据当前节点的字段配置渲染对应输入组件
   - "指定下一节点处理人"单选（结束节点提交时隐藏，提交即完成任务）
   - 提交并流转 / 保存草稿
3. 提交校验：当前处理人 = 登录用户、任务进行中、节点一致、必填字段、非结束节点需指定下一处理人

### 3.4 数据管理模块
1. 统计卡：总任务 / 进行中 / 已完成 / 我的待办
2. 任务列表：任务名 / 模板 / 当前节点 / 当前处理人 / 进度（如 2/5）/ 状态 / 操作
3. 详情弹窗：el-steps 流转进度 + 各节点表单数据查看

## 四、数据库表设计（MySQL，InnoDB，主键统一 bigint）

> 设计原则：模板元数据与业务填报数据分离，动态表单不新增数据表，采用 JSON 存储字段配置；流程节点独立成表，任务流转按节点记录。

### 表1：sys_user 用户表
账号、员工号、姓名、部门、密码、状态。

### 表2：flow_template 流程模板表
模板名称、分类、全局提示、版本号、状态、是否允许修改、创建管理员、时间。
（顺序流转模型，不再需要 flow_mode / enable_repeat_submit）

### 表3：flow_template_node 流程节点表【新增·核心】
存储模板的节点链定义。
```
id, template_id, node_name, node_key, sort_num,
node_type(1开始 2中间 3结束), assign_next(是否需指定下一处理人 0/1),
node_tips, create_time
索引 (template_id, sort_num)
```

### 表4：flow_template_field 模板表单字段表
每个节点的字段配置。在原表基础上增加 `node_id`（字段归属节点）。
字段：template_id、node_id、field_key、field_label、field_type、sort_num、required、placeholder、field_tips、max_length、enum_options(json)、file_max_size、file_suffix、multiple_file。

### 表5：flow_task 填报任务表
在原表基础上增加流转指针字段：
```
current_node_id        当前节点ID
current_handler_id     当前处理人ID
finished_node_count    已完成节点数（默认0）
total_node_count       总节点数（默认0）
索引 idx_current_handler(current_handler_id)
```

### 表6：flow_task_node 任务流转节点表【新增·核心】
任务实际流转记录，每个节点一条，记录处理人、处理状态、表单记录。
```
id, task_id, node_id, node_name, sort_num, node_type,
handler_user_id, submit_status(0待处理 1已处理),
handle_time, next_handler_user_id, form_record_id, create_time
索引 (task_id, sort_num)、(handler_user_id, submit_status)
```

### 表7：flow_form_record 表单填报主记录
每个节点处理人提交生成一条。在原表基础上增加 `node_id`、`task_node_id`。
字段：task_id、template_id、node_id、task_node_id、user_id、record_status、is_draft、submit_time。

### 表8：flow_form_data 表单字段填写数据表
存储每个字段填写的值（文本/日期/数字/枚举值/文件名）。

### 表9：flow_attachment 附件文件表
统一管理上传文件。

> 废弃：flow_task_user（保留表和代码不删，停止使用；新流程用 flow_task_node 承载处理人）

## 五、关键业务流程时序

### 流程1：管理员设计流程模板
1. 创建 flow_template（模板主表）
2. 设计节点链：添加节点（下发/需求设计/.../结束），设置节点属性
3. 为每个节点配置字段 → flow_template_field（带 node_id）
4. 保存流程：写 flow_template_node + flow_template_field，版本 +1

### 流程2：管理员下发任务
1. 选模板，新增 flow_task（锁定 template_version，current_node_id=首节点，current_handler_id=首节点处理人，total_node_count=n）
2. 插入首个 flow_task_node（handler=首节点处理人，submit_status=0 待处理）
3. 任务生效，首节点处理人待办可见

### 流程3：处理人提交并流转（核心事务 submit）
1. 校验：当前处理人=登录用户、任务进行中、current_node_id 一致、必填字段、非结束节点需 nextHandlerUserId
2. 插入 flow_form_record（带 node_id、task_node_id）
3. 批量插入 flow_form_data
4. 更新当前 flow_task_node：submit_status=1 已处理、handle_time、next_handler_user_id、form_record_id
5. 查下一节点：
   - 有下一节点 → 插入新 flow_task_node（handler=nextHandlerUserId，待处理）+ 更新 task 指针（current_node_id、current_handler_id、finished_node_count+1）
   - 无下一节点（已是结束节点）→ task.status=2 已完成
6. 下一节点处理人待办可见，循环直至结束

## 六、扩展点与优化建议
1. 权限细化、消息通知（站内信/企微/钉钉）
2. 分支流转：当前纯线性，后续可在节点配置分支条件
3. 表单联动：字段显隐联动规则
4. 数据导出：表单数据 + 附件打包下载
5. 附件对象存储：第一版存文件名文本，后续接 MinIO/OSS

## 七、潜在坑点提醒
1. 修改模板必须版本化，已下发任务沿用旧版本节点与字段
2. submit 流转必须事务化，避免节点记录与任务指针不一致
3. 并发提交需用 currentNodeId 一致性校验防止重复流转
4. 结束节点 assign_next=0，提交即完成任务，不再指定下一处理人
